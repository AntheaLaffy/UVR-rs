# Rust 推理方案：先验草案

日期：2026-09-09。状态：供本轮讨论的可修订方案，未完成权重、算子或整模型验证，不代表后验结论。用户指定的四套模型见 [任务](tasks.md)；本文件中的实现拆分、候选依赖、默认参数和实施顺序均为先验假设。

## H01：三个网络实现覆盖四套权重

| 计划实现 | 目标权重 | 预计网络输出 |
| --- | --- | --- |
| BS-RoFormer | viperx 1296 | 人声复数频谱掩码，再重建人声；伴奏通过对齐的混音减人声得到 |
| VR CascadedASPPNet（旧版 HP） | 5_HP-Karaoke-UVR、6_HP-Karaoke-UVR | 实数频谱掩码；两套权重分别绑定完整预处理与输出配置 |
| VR CascadedNet（新版，含双向 LSTM） | UVR-DeEcho-DeReverb | 实数频谱掩码；按参考定义映射干声与混响／回声侧输出 |

证据入口是 [后验 K002／K003](posterior-knowledge.md)，但“这三个实现足以加载四套实际权重”仍需验证。不能以模型名称或文件大小最终决定网络变体；应核验张量键、形状、权重校验和与配置。

5-HP 与 6-HP 预计共用网络代码，不能因此默认共用频带配置。Karaoke 对完整混音的输出可能包含伴奏与和声，需在人声输入上核对主唱／和声语义。DeEcho 是学习得到的分离网络，不计划另加传统回声抵消或 WPE 算法替代指定权重。

验证与修订条件：实际 checkpoint 出现未覆盖的层、容量、频带或输出定义时，修订实现拆分，而不是修改权重凑形状。

## H02：共用 DSP 基础，保留两条处理管线

| 管线 | 计划流程 |
| --- | --- |
| RoFormer | 立体声波形分块 → STFT → 复数频谱布局／分频带 → 网络 → 复数掩码乘法 → ISTFT → 波形块加权合成 → 残差伴奏 |
| VR | 多采样率音频 → 各频带 STFT／声道变换 → 裁剪拼谱 → 幅度归一化 → 滑窗预测掩码并裁有效区 → 掩码调整 → 分频带重建、逆声道变换与重采样合成 |

公共算法包括 FFT、STFT／ISTFT、窗函数、padding、抗混叠重采样、复数运算、声道与增益处理、长度对齐、分块调度和缓冲复用。共享基础函数不表示共享参数或整个调度器。

具体兼容边界：

- 保留频谱 Nyquist bin、窗的周期性、中心 padding、FFT 缩放和 ISTFT 窗能量归一化。
- 支持 VR 配置中的非 2 次幂 FFT 尺寸，不把所有频带固定为 2048 点。
- RoFormer 分频带使用指定配置，不能替换为 Mel 频带；复数实虚部与声道排列必须对齐。
- VR 按参考版本区分声道变换、滤波与裁剪；滑窗有效区域拼接不同于 RoFormer 波形块加权合成。
- 区分整段／整曲幅度归一化与逐块归一化；为节省内存改变策略前先验证是否改变输入分布。
- 重采样不仅比较频响，还比较延迟、边界和输出采样数；替换重采样器不能默认数值等价。

验证与修订条件：对脉冲、合成信号、静音、短片段及客户素材逐阶段比较参考结果；差异明显时调整兼容层，而非只在最后归一化音频掩盖误差。

## H03：算子范围

### BS-RoFormer

计划支持频带投影、Linear／矩阵乘、RMSNorm、RoPE、多头缩放点积注意力、Softmax、注意力门控、残差、GELU 前馈网络、按频带的 MLP／Tanh／GLU 掩码头，以及 reshape／transpose／split／concat 等布局操作。

使用参考配置定义的时间轴与频带轴注意力。CPU 第一版先验证精确注意力；如内存不允许直接形成完整分数矩阵，可研究保持全局 Softmax 语义的分块算法，不能用局部注意力冒充等价实现。FlashAttention 不是首个 CPU 基线的实现前置条件。

### VR 旧版 HP

计划支持 Conv2d、group／depthwise／空洞卷积、BatchNorm 的推理行为、ReLU／LeakyReLU、ASPP、多级编码解码、沿指定轴的平均池化、双线性上采样、跳跃连接、裁剪、复制 padding 与 Sigmoid。

重点检查双线性插值的 `align_corners`、空洞卷积 padding 和拼接轴；可运行的近似 U-Net 不能视为指定 CascadedASPPNet 的实现。

### VR 新版 DeEcho

在新版级联结构的卷积与 ASPP 算子外，支持双向 LSTM、输出投影和 BatchNorm1d。不能只在旧版网络末尾追加 LSTM。

需要核对 LSTM 的门顺序、两组 bias、反向序列遍历、输出恢复时间顺序、双向拼接和状态初始化。窗口之间是否保留状态由参考行为决定，不能为了流式处理自行连续传递。

### 推理与训练的分界

训练损失、优化器、反向传播、训练时数据增强、辅助损失输出头不列入首版执行范围。注意网络内部用于后续级联的中间特征仍是推理必需，不能因变量名含 `aux` 而删除。

BatchNorm 折叠属于后续优化假设：先对齐 eval 行为，再验证折叠前后的误差。Dropout 按推理状态关闭。

## H04：兼容选项分阶段验证

VR 的 aggressiveness、TTA、merge_artifacts 与高频 mirroring 列入兼容范围，按选定参考预设逐项接入。建立第一个基线时可与参考程序一起关闭可选项，但不能把关闭后的输出称为客户原预设的复现。

音频入口先建议用 WAV／浮点 PCM 做数值验证；其他输入格式作为后续解码层扩展。此建议不代表最终产品只支持 WAV。

## H05：Rust 技术栈候选

| 层 | 待验证候选 | 成立条件 |
| --- | --- | --- |
| 张量与神经网络 | Candle CPU 与 Burn 的合适 CPU 后端并列；原生后端约束确定后评估 ONNX Runtime，ONNX Rust 路线另看 tract／burn-onnx | 特殊卷积、插值、LSTM、归一化和注意力可正确表达，CPU 耗时、内存与依赖分发可接受 |
| FFT | RustFFT | 支持所需尺寸、归一化与平台构建，能与参考 STFT 对齐 |
| 重采样 | 先明确参考算法；Rubato 作为候选 | 频响、边界、延迟、长度及整模型质量达标；必要时实现参考算法的兼容路径 |
| 权重 | 手写网络候选为 safetensors + 显式模型配置；ONNX／Burn 导入路线另核对其产物格式 | 转换后张量名称、形状、dtype、数值和权重标识均可核验 |

Candle 官方 [依赖与 feature 定义](https://raw.githubusercontent.com/huggingface/candle/main/candle-core/Cargo.toml) 将 MKL／Accelerate 等列为可选项；[LSTM 源码](https://raw.githubusercontent.com/huggingface/candle/main/candle-nn/src/rnn.rs) 提供可供核对的门计算与权重命名。这是选择验证对象的依据，不能证明完整 VR 或 1296 已受支持。

[RustFFT](https://docs.rs/rustfft/latest/rustfft/) 和 [Rubato](https://docs.rs/rubato/latest/rubato/) 是基础 DSP 候选。依赖版本及特性在开始实验时固定；本轮不添加 Cargo 依赖。

本轮修订：此前“Candle 优先、Burn 后备”的排序依据不足。两者并列比较，ONNX Runtime 与 ONNX Rust 路线也进入讨论；原生运行时的产品采用仍取决于纯 Rust 边界。具体比较及专用实现的采用条件见 [框架与专用实现先验](backend-priors.md)。不预设任一框架必然更快。

2026-09-10 已确认运行时不依赖 Python，独立验证可用 Python／PyTorch。推理实现仍优先纯 Rust；LibTorch／ONNX Runtime 等原生核心是否可作为产品依赖，仍取决于未确定的 FFI 边界。ONNX 格式本身不决定实现语言。底层系统调用、计算库与未来 GPU 驱动另行核对，不能把允许验证工具解释为选定产品后端。

验证与修订条件：先用固定版本及真实模型形状跑算子对照和峰值内存实验，再决定是否采用该框架及权重方案。

2026-09-12 进展：按后续性能目标，OpenVINO CPU 已作为可选实验特性接入 core／CLI，使用安全 Rust 绑定、原始 checkpoint 和 Rust 内存构图，运行时不依赖 Python。此入口用于检验实际任务收益；默认后端、原生库分发和平台支持范围仍以完整验证为准。GPU 运行时也已安装并开始实测，具体故障、队列对照和采用范围见 [完整后端实验](../benchmarks/2026-09-11-roformer-openvino.md)。

## H06：CPU 基线与组织方式

首个产品验收平台为 Linux CPU；后续性能实验同时评估本机可用 GPU，不以原两线程 CPU 对照限制最终配置。Windows 客户硬件与运行验证仍需单列。

建议基线为 FP32、batch=1、一次加载并运行一个模型。保留完整模型权重和架构，不以量化、裁层或换小模型作为默认适配方法。线程数通过测量决定；控制外层任务与算子内部并行的叠加。

计划在 `uvr-core` 内按 `audio`、`dsp`、`models`、`inference`、`weights` 的职责组织模块：公共音频处理、三个具体网络、各自调度与模型配置。先保留一个实现后端，不预建通用多框架插件系统。CLI 与 GUI 共用 core，权重按需加载。

分块与缓冲复用必须尊重归一化和边界语义；首次用少量片段验证，稳定后扩大到整曲。不会据 FP32 或 Rust 本身承诺实时推理。

验证与修订条件：记录分阶段耗时、峰值 RSS 和输出误差，按 [性能协议](performance.md) 决定线程数、缓存方式及后续优化。在实际内存可承受的范围内，允许更大 batch、工作缓冲与缓存换取速度。本机 GPU 实验不能代替 Windows 运行验证。

## H07：建议实施顺序

1. 固定权重、配置和参考版本；建立纯 CPU 的 DSP 对照样本。
2. 提前做 RoFormer 注意力／RMSNorm／掩码布局、VR 特殊卷积／上采样以及双向 LSTM 的小规模兼容性实验，尽早暴露框架风险；随后用真实配置形状评估内存和耗时。
3. 首个端到端目标选择 5-HP，覆盖旧版 VR 管线；接着验证 6-HP 的权重与配置切换。
4. 完成新版 VR 与 DeEcho，验证 LSTM 和输出语义。
5. 完成 1296 的整模型及长音频调度，最后串联用户处理流程。1296 的关键风险在步骤 2 提前验证，不等到最后才评估可行性。

这个顺序基于复用 DSP 和分阶段引入算子的假设，不代表 VR 在 CPU 上必然更快。若 1296 可行性或客户优先级要求提前，调整端到端顺序。
