# 先验知识与待定问题

记录日期：2026-09-09。这里存放实现前的要求、经验反馈与假设；经验证的事实转入 [后验知识](posterior-knowledge.md)，并保留证据。模型清单以 [任务](tasks.md) 为准。

## 来源为客户反馈

- 客户指定 1296 处理伴奏，认为其比 MDX23C 更符合速度与效果要求。
- 客户认可 5-HP／6-HP Karaoke 的去和声效果。
- 客户认可 DeEcho-DeReverb 的去混响与 delay／echo 效果。

这些是目标素材上的选型输入，不是跨数据集的性能排名，也不是本项目实测结论。此处 delay 指音频中的延迟效果；若实际需求是轨道时间对齐，需要另行明确。

## 已确定偏好

推理优先纯 Rust，GUI 不受此约束。此前讨论中的 Rust + ONNX Runtime 只是候选建议，未获选用，不作为项目默认方案。Tauri、TypeScript 和未来可能的 dsh 集成来自原有 `gui/Agent.md`；首版排除 AI 基础功能。

## 需要验证的判断

| 假设 | 验证方法 |
| --- | --- |
| 三个网络实现可以覆盖四套指定权重 | 检查实际权重张量、网络变体和完整参数映射，运行参考推理 |
| 共用 DSP 层能覆盖 RoFormer 与 VR | 分别对齐窗函数、padding、重采样器、频带裁剪与重建结果 |
| 先分人声，再去和声，再去混响适合作为处理链 | 同一素材比较去和声与去混响的不同顺序及每一步输出 |
| 纯 Rust 路线能满足性能目标 | 明确硬件与预算后，对关键算子和完整模型测量 |
| 同一权重在不同程序中能得到近似结果 | 固定程序版本和预设，检查分块、后处理、精度与增益差异 |

“用 Rust”本身不是加速证据。框架算子覆盖、内存布局、GPU 内核、分块策略与线程调度都可能决定实际表现。

## 推理方案讨论清单

1. CPU、CUDA、Metal、其他 GPU 后端的优先顺序是什么？
2. 纯 Rust 是否允许调用底层 GPU 计算库？是否允许离线使用 Python 转换权重或生成参考结果？
3. 先验证哪一个模型与哪一种数值精度？正确性误差阈值如何确定？
4. 接受固定分块长度还是需要动态长度？参考 UVR 的哪些可选后处理必须兼容？
5. 音频格式、最长输入、内存上限、输出位深与采样率要求是什么？

这些问题在初始化后讨论。当前没有选择 Candle、Burn、ONNX Runtime、LibTorch，也没有承诺支持的加速平台。
