# 性能协议与优化实验

状态：2026-09-13，已有 [卷积模块](../benchmarks/2026-09-10-vr-cpu-blocks.md)、[LSTM／RoFormer 模块](../benchmarks/2026-09-10-sequence-cpu-blocks.md)、[5-HP／6-HP 完整掩码网络](../benchmarks/2026-09-10-hp-cpu-network.md) 和 [DeEcho 完整掩码网络](../benchmarks/2026-09-10-deecho-cpu-network.md) 的 CPU 记录，以及 [VR 文件处理与真实片段](../benchmarks/2026-09-11-vr-cli-audio.md) 的正确性对照。整曲及处理链尚未完成性能验收。性能目标、速度优先的内存策略及质量阈值由 [工程基线 v1.3](baseline.md) 固定；以下候选方向不代表已经实现或完成调优。

目标是在既定音质下充分压榨推理性能，覆盖四套模型及完整处理链。两线程、FP32、batch=1 用作固定资源对照；另测充分利用本机硬件的最佳配置。与 Python 参考相比仍慢的路径不能通过性能验收，超过参考也不是停止优化的条件。每轮按实测热点选择投入，复测完整任务的速度、内存和响应；适用的高收益方向必须实际验证，保留采用／拒绝理由和剩余瓶颈。

### 优化范围原则：热点优先，但不只优化热点

性能采样用于确定优先级、估算收益上限和避免凭直觉改动；它不是优化范围的硬性边界。除 GEMM、卷积和注意力等主要热点外，也要检查会在每个窗口、每层或每次阶段边界重复发生的“小开销”：临时分配与清零、flatten／reorder／transpose、重复校验和扫描、边界分支、调度与同步、进度回调、缓存失效以及网络前后的数据搬运。这些开销单次占比可能很低，但在长音频或高并发下会累积，并可能放大内存带宽和调度压力。

采用顺序遵循“热点优先、全链路覆盖”：先处理有明确大头证据且风险可控的路径，同时为每个阶段保留至少一个端到端候选检查。任何边角优化都必须在同一协议下报告完整任务墙钟、网络／前后处理阶段、RTF、RSS／swap 和质量门限；局部计时下降不能替代整链路收益，局部采样占比低也不能单独作为拒绝理由。只有当候选在交错 A→B→A 或等价重复实验中显示可重复端到端收益时才保留，否则记录证据并撤回。

当前执行顺序：先完成 Burn CPU 的 5-HP、6-HP 和 DeEcho 网络及完整 VR 处理链；RoFormer 网络优化暂列最后，已有 RoFormer 改动只保留为可复现的阶段性记录，不与 VR 的性能结论混用。

VR 窗口并发路径已把 batch=1 的在途输入缓冲移到并发组外复用，避免长音频按组重复分配、清零和 flatten；5-HP 并发 4 的真实音频质量检查通过。当前证据只证明分配路径和输出语义，尚不足以单独宣称墙钟加速，后续必须用同一构建交错 A→B→A 复测并报告分配、RSS、swap 和完整任务耗时。

已拒绝一个归一化候选：把整段频谱 `magnitude` 预先除以全局最大值，理论上可避免重叠窗口重复除法，但 10 秒/4 窗/并发 4 实测为 `28.031 s`，慢于既有同协议 `23.928 s`；质量通过但候选已撤回。该结果说明 VR 的热点不能只按算术操作数判断，还要计入额外全谱遍历、缓存压力和调度成本。

常量归一化乘法候选也已拒绝：把窗口复制热循环中的除法替换为预计算倒数乘法，质量门限通过，但同一 native 10 秒完整任务两次复测为 `RTF 2.426/2.353`，高于当时旧 native 记录约 `2.09`，未观察到可重复收益，代码已恢复原表达式。

窗口结果归并的边角优化已保留：并发 HP 路径不再把多个窗口输出 flatten 到新向量后再全量扫描，而是逐窗口校验并直接写入 mask。10 秒 5-HP、8 线程、并发 4 的 A1/A2→B 复测为总耗时 `23.455/23.685→22.642 s`，RTF `2.346/2.368→2.264`，质量门限通过；这类分配、复制和重复遍历虽然不是最大采样热点，但在长音频窗口并发下会累积成可测端到端收益。

同一原则也淘汰了一个低层算术候选：`resize` 坐标表预计算 `1 - weight` 虽通过数值检查，却在同协议 A→B 中使总耗时从 `22.159 s`（RTF `2.216`）退化到 `23.274 s`（RTF `2.327`），因此已撤回。边角优化仍需以完整链路结果决定取舍。

`finish_mask` 的直接连续存储复制候选同样撤回：完整质量检查通过，但 A2/B 为 `22.275/22.433 s`（RTF `2.228/2.243`），略有退化。Burn 张量的 cat/slice 不能仅凭源码表面操作数判断，必须以端到端实测决定。

Winograd tile 粒度补测也完成：`TILE_BATCH=256` 为 `22.831 s / RTF 2.283`，`1024` 为 `24.328 s / RTF 2.433`，都慢于 `512`，故保持 `512`。较小和较大的工作集分别暴露调度开销与缓存压力，不能仅按 GEMM 调用次数选择 tile。

最佳 VR 软件配置已完成本机 native 构建：`RUSTFLAGS='-C target-cpu=native'`、`TILE_BATCH=512`、HP 窗口并发 4、`RAYON_NUM_THREADS=8`。在此基础上，Winograd 的 36 个独立平面直接调用 `gemm` 微内核，绕过每个 tile 组的 Burn batched-matmul 包装，并把只读变换权重存成 `[input, output]` 的原生列主序布局，减少 GEMM lhs packing；每次 forward 只分配并清零一次最大 scratch，复用到所有 tile 组，同时预计算 tile 坐标和输出 product 偏移。unsafe 仅位于带 shape／stride／slice 长度断言的单一 helper，workspace lint 保持 warning 而非无条件放开。scratch／坐标／偏移组合的 5 次 warm 样本为 `RTF 1.985/2.027/1.979`（网络 `19.113/19.592/19.171 s`），相对旧 native 约 `RTF 2.255` 明显改善；扩大到 7-run 的 5 个 warm 样本为 `1.987/2.023/2.023/2.042/2.165`，中位数 `2.023`，所以尚未宣称稳定越过 2.0。质量门限通过，最大绝对误差 `7.15e-7`、RMSE 约 `3.6e-8`。该 native + 微内核结果只代表当前 i5-13420H 和系统调度，不能直接作为跨机器分发默认；ThinLTO 因 proc-macro 限制未采用。

`target-cpu=native + codegen-units=1` 的编译器实验也已完成：独立产物在同协议下为 `23.057 s / RTF 2.306`，慢于普通 native 的 `22.551 s / RTF 2.255`，并将构建耗时拉长到约 8 分钟，因此不采用。编译器参数必须以完整任务收益验证，不能因生成更激进或更小的代码就默认有效。

硬件亲和性也完成了交错实验。本机性能核 SMT 线程为 CPU 0–7，能效核为 8–11；绑定物理核集合或只绑定性能核都没有稳定收益。性能核集合的默认→绑定→默认 RTF 为 `2.326→2.341→2.275`，因此 native 默认继续交给系统调度，避免把单次亲和性样本误报为优化。

VR 第一轮目标为 `RTF <= 2.0`。scratch／坐标／偏移优化后 5-run 中位数约 `2.0`，但 7-run 中位数为 `2.023`，仍未完成稳定验收；下一步继续围绕 Winograd 变换、GEMM 形状／布局、权重 packing 和硬件指令利用率做采样驱动优化。RoFormer 网络继续延后处理，不与本轮 VR 结论混合。

2026-09-12 用户明确选择速度优先：在机器可承受的实际内存范围内，允许增加预打包、缓存、scratch、batch 和并发的内存投入。原 VR 4 GiB／1296 8 GiB RSS 上限撤销；按任务峰值、系统可用内存和前台应用余量控制规模。这里的“速度优先”是有条件的：额外内存必须能归因于有效的权重预打包、复用缓存、并行在途窗口或减少搬运的 scratch，并在完整任务墙钟、RTF 或稳定吞吐上给出可重复收益；只增加 RSS、复制数据、调度和带宽压力而不提速的内存是垃圾占用，应拒绝。OOM、明显内存压力以及导致任务或交互变慢的换页须避免。比较内存策略时同时报告速度、CPU 时间、RSS 和 swap，不能只为降低 RSS 撤回更快的实现，也不能用“内存很大”替代提速证据。

本轮实现与原始记录见 [VR CPU 优化实验](../benchmarks/2026-09-11-vr-cpu-optimization.md)：归一化／激活融合已完成三套 VR 的真实片段五次热运行；Winograd 跨窗口 tile GEMM 已通过 5-HP／6-HP 数值检查，但 batch=2 只在 5-HP 的完整 PCM 上获益，6-HP 反而退化，因此产品默认保持 batch=1。5-HP 的 8 线程在本机完整 PCM 上比 2 线程减少约 34.5% 耗时，其他模型及后端继续测量。后续仍以矩阵乘、变换、布局及硬件利用为重点。

[1296 CPU 优化实验](../benchmarks/2026-09-11-roformer-cpu-optimization.md) 记录完整窗采样、RoPE／RMSNorm 融合与 GELU 并行的模块对照，以及 OpenVINO FP32 模块候选。通用布局遍历和串行逐元素运算已有明确热点证据；完整网络、实际文件与最佳后端的性能结论仍按各自验证范围记录。

[OpenVINO 完整后端实验](../benchmarks/2026-09-11-roformer-openvino.md) 已推进到 1296 单窗完整 PCM，并安装核显运行时验证 Rust 调用。CPU 五次热运行全部通过双轨门限；GPU 的事件等待故障在 Rust 和 Python 均复现。安装 Intel OpenCL 诊断层后，顺序队列三个独立进程共 21 次通过，恢复乱序队列则再次超时。该方向还需更多窗口、整曲响应和分发验证，不能据单窗结果宣布调优完成。

2026-09-12 已补齐 Rust 从原始 `.ckpt` 构图的路径：301 帧 CPU／GPU 完整热运行通过，801 帧 GPU 单次正确性通过。可选 OpenVINO CPU 接入 core／CLI，共享分窗、重采样与残差，真实 WAV、四组短音频、取消及请求复用验证通过。CPU 实验约 8.5～8.7 GiB 的 RSS 按上述速度优先策略评估；完整窗口重复、整曲、缓存／批次及 GUI 仍在推进。

Burn CPU 的 1296 路径已采用经实测的速度优先默认值：线性层使用 flattened layout，时间／频率注意力批次为 `62/301`（时间序列本身为 801 帧；301 是实测的频率批次折中，不是帧数）（`UVR_LINEAR_LAYOUT=flattened`、`UVR_ROFORMER_TIME_BATCH=62`、`UVR_ROFORMER_FREQUENCY_BATCH=301`）。在同一 8 线程真实窗口上，默认小批次的网络耗时约 107.4 s，`62/301` 批次约 103.7 s，叠加 flattened layout 约 88.5 s；三者均通过原有 FP32 波形门限。该配置峰值 RSS 约 1.19 GiB，环境变量仍可显式降批次或切回 batched layout，以便低内存设备和 A/B 实验；不能把单窗结果外推为整曲验收。

频率分支在 `swap_dims(1, 2)` 后现在只做一次显式连续化，避免每个 flattened 线性层重复处理 stride；完整批次还跳过单元素 `Tensor::cat`。短 `signal` fixture 的更新后二进制 7 次均通过完整波形检查，耗时范围 `1.784–2.815 s`、中位数约 `2.49 s`。这只是布局级短窗口证据，必须在同一 8 秒真实窗口上完成 A→B→A、RSS 和网络阶段计时后，才能把收益计入正式端到端结论。

最新真实 `local_audio` 单窗复测（8 线程、默认 `62/301`、flattened）网络耗时 `82.445 s`，进程墙钟 `85.67 s`，峰值 RSS `1,190,648 KiB`，swap 为 0，双轨质量门限通过；产物见 `benchmarks/artifacts/2026-09-11-roformer-performance/burn-contiguous-real-t8.{json,time}`。此前未做频率连续化的相同配置记录约 `88.5 s`，但尚未完成交错 A→B→A 和多次完整窗口重复，因此这里只记录为方向性收益，不能作为最终稳定加速比。

## 测量对象

分别测量四套权重及最终处理链。先验证数值和音质，再比较性能；每次只改变声明的实验变量，其余输入、分块、重叠、batch、精度、TTA、aggressiveness、高频处理和输出编码均固定。不得把关闭后处理带来的速度变化记为同质量加速。

| 指标 | 定义 |
| --- | --- |
| 冷启动耗时 | 新进程启动到完成首个任务，包含模型加载与后端初始化；注明文件系统缓存是否受控 |
| 热运行耗时 | 同一进程复用已加载模型的完整任务时间 |
| RTF | 处理墙钟时间 / 输入音频时长，越低越快；明确计时是否包含 I/O |
| 处理倍速 | 输入音频时长 / 处理墙钟时间，即 1 / RTF |
| 分阶段耗时 | 解码、重采样、STFT、网络、ISTFT／重建、编码分别记录 |
| 峰值资源 | 进程 RSS 与可获取的设备显存分别记录，注明采样方式与间隔 |
| CPU 执行 | 墙钟、user／sys CPU 时间、实际活跃线程数、逐线程／逐逻辑 CPU 利用率及统计区间；注明单 CPU／整机归一化口径、亲和性与 CPU 配额。可获取时记录 cycles、instructions／IPC、缓存及分支未命中、上下文切换与核心迁移，解释见 [低占用诊断](#低-cpu-占用的诊断) |
| 数据搬运 | 解码／编码 I/O、张量 reorder／copy 字节数、分配次数及临时缓冲峰值分开统计 |
| 交互响应 | 首次进度、每窗耗时、取消请求到停止的延迟；同时检查 GUI 响应 |
| 质量 | 对参考结果的波形／频谱误差与残差，必要时有真值数据上的 SDR／SI-SDR 和客户听评 |

GPU 计时必须同步或使用设备计时事件，避免只测到异步提交。统一内存设备注明内存指标是否重复计算。不要通过独立归一化每条分轨掩盖增益误差。

## 执行方法

1. 固定 Git 提交、Cargo.lock、权重及配置校验和、参考程序版本和全部推理参数。
2. 使用 release 构建，记录编译特性、RUSTFLAGS、CPU／GPU、内存、驱动、系统、电源模式和线程数。
3. 单独报告冷启动；热运行先预热，再至少执行 5 次，保留全部样本并报告中位数与范围。样本足够时再报告分位数。
4. 避免多个实验争用同一设备。工具或系统限制须写入记录，不能以缺失值冒充 0。
5. 检查输出采样数、声道和增益后做误差比较，使用工程基线预先固定的阈值，不以逐轨归一化或时间平移掩盖差异。
6. 只在同一测量协议下比较；报告优化前后性能及质量变化。

关键实验缺少模块、分析工具、编译器或设备运行时，应安装所需依赖并验证后继续；用户已明确授权这种安装。Python 实验依赖优先放入隔离环境，系统驱动按实际硬件安装，记录版本、安装方式及设备／内核验证结果。不能因为当前环境缺包而降低目标、跳过重要实验，或直接判定后端／硬件不可用。安装后仍有问题时，先区分权限、驱动兼容和实际算子支持，保留具体错误及已尝试的解决方法。

## 低 CPU 占用的诊断

本项目处理本地离线音频，没有实时 RMVPE 的逐块截止时间约束，因此值得测试更大的 batch、独立窗口并发和流水线；内存、首次进度和取消响应仍须验收。窗口并发按组提交时，进度和取消至少在每个并发组完成后检查；必须记录组内最长窗口作为取消延迟，不能把组提交误报为即时取消。CPU 总占用低于 15% 是调查线索，优化目标始终是每首歌耗时、RTF 和单位墙钟时间处理的音频长度。占用率下降而任务更快可以是成功的优化；占用率升高也可能只是自旋、重复计算或资源争用。即使已有较高处理倍速，仍按剩余热点和潜在收益决定下一项实验，不用利用率或某个倍速替代调优完成证明。

### 先统一占用率口径

记录工具、采样区间，以及百分比描述的是整个系统、目标进程还是单个线程。按整机 16 个逻辑 CPU 归一化时，一个线程持续运行约占 6.25%，两个约占 12.5%；15% 约等于平均占用 2.4 个逻辑 CPU 的调度时间。`top` 等工具的进程视图可能以单个 CPU 的 100% 为单位，此时两个忙线程约显示 200%；显示模式必须注明。逻辑 CPU 的时间份额不等于等量的物理计算能力，SMT 和混合核心须单列。

在同一观测区间可用 `平均占用的逻辑 CPU 数 ≈ Δ(user + sys) / Δwall` 交叉检查；若按整机归一化，再除以逻辑 CPU 总数并乘 100%。CPU 时间也包含自旋和硬件停顿，不能将这个数当成有效计算量。逐核图还可能因线程迁移而呈现“每个核都不太忙”，必须同时看逐线程增量及实际同时执行的线程数；创建了很多线程不等于展开了计算并行。

当前 [CLI](../cli/src/audio.rs) 与 [GUI](../gui/src-tauri/src/tasks.rs) 使用共享参数与每任务 Rayon 线程池，线程默认值为可用 CPU 数与 8 的较小值；CLI 的 `--threads` 和 GUI 控件可覆盖，`RAYON_NUM_THREADS` 保留初始值兼容。具体优先级见[运行时指南](runtime.zh-CN.md)。遇到低整机占用，优先核对任务记录中的实际配置，再查可用 CPU 集合、亲和性和容器／cgroup 配额。Linux 可从 `/proc/<PID>/status` 的 `Cpus_allowed_list` 及所属 cgroup 的 `cpu.max`、`cpu.stat`（v2）核查，节流次数／时间应取观测区间增量。旧的两线程配置用于历史固定资源对照，不限制产品的最佳配置。

### 按证据区分限制来源

| 待检验原因 | 要观察的证据 | 对应实验 |
| --- | --- | --- |
| 并行度未展开 | 少数工作线程持续运行；线程池预算过小；算子因 shape／阈值选择串行；层间、循环时间步等依赖限制同时就绪的工作 | 先核对运行时／BLAS／Rayon 的配置与真实内核，再比较算子线程数和独立窗口并发；小算子测任务粒度，不强行把每个算子拆给所有核心。 |
| 数据访问限制 | IPC、缓存行为、内存流量及内核访问方式共同指向等待数据；改变布局／工作集后耗时下降。随线程增加，吞吐和实测带宽同时趋于平台值，才支持带宽饱和判断 | 比较 layout、blocking／tiling、权重打包、融合、缓冲复用和减少 copy；区分访存延迟与带宽限制。量化另走硬件能力和音频质量门限，不能由压缩比例推导速度。 |
| 同步、调度或负载不均 | 各 worker 完成时间差大；锁／barrier／队列等待；线程可运行却长时间未获调度；核心迁移、CPU 配额节流或其他任务争用 | 测每 worker 工作／等待时间、线程状态和调度轨迹，调整分区、粒度、总线程预算与亲和性。阻塞等待可能降低占用，自旋等待则可能维持高占用。 |
| 网络以外的阶段占时 | 解码、重采样、STFT、ISTFT、重叠归并、编码或 I/O 的墙钟时间占比高；搬运与分配也可能发生在网络内部 | 给各阶段建立独立计时，定位 copy／transpose／allocation 的调用来源；先优化实际主耗时阶段，再验证资源允许的流水线边界。 |

内存访问导致的 pipeline stall 通常仍计入操作系统的忙碌 CPU 时间，因此 memory-bound 内核完全可能显示高占用；不能把“所有核占用都低”直接归因为等 RAM。低 IPC 还可能来自指令依赖、分支或前端供给；高 cache-miss 比例也未必代表大量 DRAM 流量。算术强度用 `AI = FLOPs / 搬运字节数` 描述时，应注明字节数对应缓存层还是 DRAM，结合本机可持续带宽与实际执行内核判断；不套用其他机器的 GB/s 数字。

### 最小诊断顺序与工具

1. 在明确的网络执行区间，同时观察逐逻辑 CPU 和逐线程占用，核对工具归一化方式、线程池、CPU 集合及配额。`htop` 的逐 CPU 显示、`top -H -p <PID>` 可辅助观察；`ps -L -p <PID> -o pid,tid,psr,stat,pcpu,wchan:24,comm` 用于线程状态快照，其中 `pcpu` 是进程／线程生命周期平均值，不替代区间采样。命令中的 `<PID>` 须换成实际进程号。
2. 记录同一任务的分阶段墙钟时间及 user／sys 时间，将低占用区间对应到加载、DSP、网络、重建或 I/O。整段平均值可能掩盖短时满核；短片段的阶段占比不能外推为整曲结果。
3. 单独执行计数器和热点采样。对选定的完整基准命令可用 `perf stat -d -d -- <基准命令及参数>` 查看可用计数器；用 `perf record --call-graph dwarf -- <基准命令及参数>`、`perf report` 检查调用路径。这些是命令模板，须展开为本轮实际 release 程序与参数；采样产物放本轮实验目录，采样期间不并跑正式计时。保留符号并确认栈展开有效，不能把截断调用栈当作完整热点归因。
4. 若怀疑阻塞／调度，补充线程状态、锁／队列计时或调度追踪。常规 CPU 热点采样主要反映线程运行时的事件，不能单独解释线程离开 CPU 后的等待；低 CPU 时间与长墙钟差距须另找等待来源。PMU 不支持、计数器复用比例低、权限不足和混合核心事件口径不一致均记录为限制，不补造 IPC 或带宽值。
5. 根据证据比较 [算子内并行与窗口外层并行](#线程预算缓存一致性与扩展性)，再测 batch 和流水线组合。每次仍以完整任务耗时、质量、峰值内存和响应判定收益，重采样确认瓶颈是否转移。

对于阶段顺序执行、其他工作不变的对照，若被加速部分占原墙钟时间 `P`，该部分加速 `s` 倍，则理想总加速比为 `S = 1 / ((1 - P) + P / s)`。例如 `P=0.5` 时，即使该部分耗时趋近零，总加速也不超过 2 倍。这里的 `P` 必须来自阶段墙钟测量，不能用 CPU 利用率或 `perf` 采样百分比替代；阶段重叠和新增调度成本需另行建模并实测。若 copy、transpose 和分配主要出现在网络内部，还须避免与网络总时间重复计数。

## 候选方向与测试优先级

本轮 5-HP 采样的主要热点为卷积矩阵乘、张量搬运和双线性上采样；短片段的文件读写占比较小。优先从实际网络形状验证算子与数据布局，再测试线程和批次。缓存未命中率或 `memcpy` 占比本身不足以证明内存带宽饱和，应结合搬运量、IPC、CPU 利用率及改变布局后的对照结果判断。

三个 VR 模型与 1296 需要分别定位：5-HP／6-HP 以卷积网络为主，DeEcho 还包含双向 LSTM，RoFormer 包含时间／频率注意力、线性层和 RMSNorm。外部 RMVPE 材料中的 BiGRU、Mel 和 FCPE 速度数字不作为这些模型的结构或性能依据。每次消除热点后重新采样，再决定下一项投入。

### 优先验证：保持原模型与推理语义

| 方向 | 为什么值得测 | 对照方法与额外验收点 |
| --- | --- | --- |
| 卷积算法与形状专用实现 | 3×3 卷积占用大量计算；通用内核未必适合 VR 的频率／时间尺寸 | 比较现有直接／im2col 路径与适用形状的 Winograd。分别覆盖 stride、dilation、groups、尾块和补零，计入输入／输出变换及权重准备成本；用完整网络检验误差累积，不能把乘法次数下降直接当作整网加速比。 |
| 成熟 CPU 推理后端 | 后端可同时提供 SIMD 内核、布局选择、权重打包和图优化 | 在现有 Burn Flex／Candle 探针基础上评估 oneDNN、OpenVINO、ONNX Runtime。先用真实中间激活和尺寸比较，再接一套完整 VR；核查算子覆盖、回退路径、插值及激活语义。计入模型转换、初始化、布局转换和原生库分发成本，保留 Rust 产品运行、原始权重加载及运行时不依赖 Python 的边界。 |
| 张量布局与缓存局部性 | 每层恢复 NCHW、反复 transpose／copy、冲突的平面步长都可能抵消快速矩阵乘的收益 | 比较连续布局、通道分块布局和后端选择的内部格式；尽可能跨层传播布局。单独测拼接、上采样、Winograd 变换及 reorder，记录字节数、缓存表现与整网时间；仅在接口边界转回标准布局也必须包含在计时中。 |
| 权重预打包与计划缓存 | 权重固定，重复重排、GEMM 打包、JIT 或 FFT 规划应与窗口执行分离 | 比较每窗准备与加载时准备；按权重身份、shape、dtype、设备和后端版本区分缓存。记录加载时间、热运行和常驻内存，检查模型／尺寸切换后缓存失效；持久缓存还需验证重启和版本变化。 |
| 算子融合 | Conv→BN→激活、MatMul→bias→激活会产生多次中间张量读写 | 分别测试推理态 BN 折叠和后端 post-op，再测组合收益。固定 epsilon、ReLU／LeakyReLU／GELU 定义与增益；检查完整两轨音频。单纯把几个调用包装进一个函数不算内存访问融合。 |
| 固定 shape 与缓冲复用 | 频繁分配和临时张量复制增加系统时间与内存压力 | 以默认 512 帧和实际尾窗为主，比较按窗分配与复用 scratch／workspace、中间激活生命周期规划。保留尾块有效长度与补零语义，检查旧数据残留、取消、失败重试及并发任务隔离；记录分配次数和峰值 RSS。 |
| 并行框架与硬件协同 | 算子、窗口和原生库可能各有线程池；混合核心与 SMT 会影响缓存和稳定性 | 先固定 batch=1，依次测 1／2／4／8／12 线程中本机适用的配置，再比较系统调度、性能核绑定和 SMT。改变后端时记录 Rayon／BLAS／运行时各自的线程预算及实际活跃线程；默认使用单层主导并行作为对照。NUMA 仅在相关硬件上测，电源策略固定并记录；并行层次与扩展性见 [HPC 实验](#hpc-与并行优化实验)。 |
| 推理 batch | 多个独立窗口可能提高矩阵乘利用率，也可能增加激活内存和取消延迟 | 比较 batch=1／2／4 的每窗时间、吞吐、首批进度、取消延迟和 RSS；固定同一组窗口及输出顺序，使用内容不同的样本检查串批和广播错误，覆盖尾部不足一批。区分音频窗口 batch、并发的 batch=1 任务与算子内部 tile；窗口依赖和归并规则见 [HPC 实验](#hpc-与并行优化实验)。 |

### 两类算法的对称探索要求

VR 卷积网络和 1296 RoFormer 的算子结构不同，但性能调优不能只在其中一个系列上试验后就把结论推广到另一个系列。每个具有现实收益可能的方向都必须在两个系列各做至少一次同协议探索；若方向因模型依赖或后端能力确实不适用，也要记录结构性原因、替代实验和拒绝证据。一个系列的“未测”不能写成另一个系列的“无需测”。

| 方向 | VR 系列必须检查 | RoFormer 系列必须检查 | 通过条件 |
| --- | --- | --- | --- |
| 层内 batch／窗口外并发 | Winograd／卷积 batch、独立频谱窗口并发 | 时间／频率注意力 batch、独立 8 秒窗口并发 | 完整任务墙钟下降，质量、取消和 RSS 通过；无收益的 batch 不保留 |
| 线程、亲和性和调度 | Rayon、GEMM、混合核心及 SMT | Burn attention／线性层、窗口调度及相同核心集合 | 在相同总线程预算下有可重复吞吐收益，不以 CPU 百分比代替 |
| 布局、预打包、融合和 scratch | NCHW／Winograd tile、权重变换、激活复用 | QKV／线性布局、RoPE／RMSNorm／GELU、STFT 和窗口缓冲 | 搬运或算术减少能映射到完整网络收益，新增内存有明确用途 |
| 成熟 CPU 后端 | OpenVINO／Candle／oneDNN 等真实卷积形状 | OpenVINO／其他图后端的真实注意力形状 | 从原权重加载到完整 PCM 的端到端结果，并记录运行时依赖 |
| SIMD／手写内核和精度 | Winograd 变换、卷积和 resize | attention、矩阵乘、归一化和 FFT 周边 | ISA、误差和可分发性满足基线；局部内核加速需通过整网复测 |
| GPU、流水线和窗口参数 | 可用设备上的整套 VR 音频链 | 可用设备上的整套 RoFormer 音频链 | 计入传输、同步、编译、设备内存和跨窗口归并；不以单个 kernel 结论替代 |

每轮实验报告两个系列的变量、输入、线程预算、质量结果和拒绝原因。当前默认配置只从已在对应系列完整任务上证明有效的候选产生；跨系列差异只能改变实现方式和优先级，不能跳过探索。

### 专项验证：先确认硬件和语义条件

| 方向 | 实验重点 | 采用条件与限制 |
| --- | --- | --- |
| INT8／BF16／FP16 与混合精度 | 根据实际 ISA 和后端能力选择精度，分别测试卷积、线性层、循环层以及量化／反量化成本。INT8 使用固定校准集和独立验证集；记录逐层／逐通道量化参数和真实执行内核。 | CPU 支持某种存储或转换格式不等于有对应的高速运算；不能默认 FP16／BF16 快于 FP32。优先保留 DSP、归一化和敏感输出层的既定精度，1296 不得绕过已经验证的 float64 正向 STFT 约定。不满足当前音频门限的方案不进入现有预设；INT4 需先证明该卷积／注意力工作负载有合适内核。 |
| 编译与 SIMD | 按下文 [编译器优化实验](#编译器优化实验) 比较目标 CPU、LTO、codegen-units 和 PGO；用优化诊断及汇编确认热点变化。 | 保持模型、后端、线程、输入和浮点语义固定；记录编译／链接成本、产物大小及兼容范围。编译参数收益与模型图优化分别归因。 |
| CPU／GPU 分工 | 在可用的 Vulkan 等设备上评估整网常驻 GPU，比较 CPU DSP＋GPU 网络与 CPU 全链路；记录传输、同步、kernel 启动、设备内存、首次编译和稳定运行。 | 驱动可枚举设备只说明具备试验条件。核显共享内存仍有同步、复制和带宽竞争；尽量避免逐层跨设备搬运。必须同步计时并通过整轨数值检查，不能由单次 GPU GEMM 推导整网收益。 |
| 窗口长度与重叠计算比例 | 固定模型，独立比较 512／1024／2048 帧等合法窗口；记录有效输出帧／计算帧比例、总窗口数、内存和取消延迟。 | 改窗口会改变边界上下文，属于参数实验，不预设与原输出等价。完整验证接缝、尾部、弱人声及混响，并与原预设音频比较；不得靠减少必要上下文或重叠隐含降低质量。 |
| DSP 与不变计算复用 | 先检查重复范围，再测试窗函数、FFT plan、索引／插值系数和模型加载的复用；只有测到重复帧计算才评估增量 STFT／频谱缓存。 | 当前 VR 已整段分析一次，再切幅度谱窗口，不能套用“每窗重算全部 STFT”的假设。RoFormer 的按窗 STFT 涉及反射边界、帧对齐和精度约定，复用时必须验证各窗边界及短输入，不可直接用整曲 STFT 替换。 |

流式神经网络状态复用、剪枝、蒸馏及更小模型列为后续架构研究。跨窗激活复用必须证明依赖范围、下采样相位、补零及上下文一致；DeEcho 双向 LSTM 的未来上下文和 RoFormer 非因果注意力使直接沿用状态／KV cache 缺少等价性保证。改变网络结构或重训后的权重需要独立音质协议和模型身份，不能作为当前四套指定权重的等价加速。随机分支消除仅在后处理采样确认为热点时安排。

## HPC 与并行优化实验

优先研究局部性、并行性和减少数据搬运。当前 UVR 是离线文件分离，同一文件的多个窗口可提供数据并行机会；不能直接套用实时单路 RMVPE 中“batch 没有多少价值”的判断。先测单核布局与内核，再做固定工作量的多核扩展，随后比较窗口、分支和流水线调度；GPU 作为具备设备与后端条件时的独立路线。以下都是待验证方向，沿用原模型、分块和音频质量门限。

### 值得测试的并行层次

| 层次 | UVR 中的候选工作 | 对照方法与采用条件 |
| --- | --- | --- |
| 数据级 SIMD／指令级并行 | Winograd 变换、插值、逐元素运算、DSP，以及 Conv／GEMM／LSTM 的内核 | 优先连续访问和固定 stride，确认自动向量化、指令调度及成熟内核的实际执行路径，再考虑 intrinsics。单线程比较真实 shape 与尾块；多个累加器、FMA 和归约重排的数值约束见 [编译器实验](#自动向量化reduction-与-fma)。 |
| 多级 tiling／blocking 与减少通信 | 缓存／寄存器 tile、权重打包、跨层布局传播、融合和 scratch 复用 | 单独改变 tile、步长或布局，计入 pack／reorder 和输出物化。记录工作集、搬运字节数、分配次数及缓存表现，确认中间张量少写少读；随后重测多核，避免多个核心只增加内存带宽竞争。 |
| 算子内共享内存并行 | 按输出通道、连续输出区域或 GEMM tile 划分任务 | 固定总线程预算，比较串行与不同任务粒度；尽量让输出区域只有一个写入者。记录负载不均、调度、同步和归约成本，小算子保留串行对照，不能把更多任务数视为更多有效并行。 |
| 跨窗口数据并行 | 同一音频的独立窗口；batch=1 的多个并发调用与 batch=2／4 的单次调用分别试验 | 使用相同窗口集合、总线程预算及实际可用内存条件，比较每窗耗时、完整文件吞吐和取消延迟。先确认模型／后端可安全并发调用，权重尽可能只读共享，激活、scratch 与循环状态独立；计入模型副本及在途结果内存，在系统有余量时以吞吐优先。 |
| 独立分支任务并行 | [HP 首阶段低／高频网络](../core/src/vr.rs)，以及 [DeEcho 双向 LSTM](../core/src/vr/deecho.rs) 的两个方向 | 比较顺序与并行分支，固定 concat 顺序和内层线程预算。HP 后续阶段依赖前一阶段，LSTM 每个方向的时间步依赖自身 h／c，均不能直接并行展开。DeEcho 已跨时间批量计算输入投影，不能把这部分记为新增收益。 |
| 跨阶段流水线 | 全局前处理完成后的窗口准备、网络执行与结果归并；条件允许时 CPU DSP 与 GPU 网络重叠 | 先测各阶段及资源占用，再选择有收益的重叠边界。使用有界队列和背压，记录队列等待、在途窗口数、缓冲峰值与首个结果时间；完整任务耗时、取消响应和音频顺序仍须达标。 |
| 设备级 SIMT 与分工 | 可用 Vulkan 后端上的整网执行；具备 NVIDIA 设备及兼容后端时再评估 CUDA | 优先成熟内核和设备内布局／tile，分别测 batch=1 与可用批次。计入传输、启动、同步、首次编译和 CPU／GPU 争用；核显共享内存也不能省略这些成本。逐层跨设备和多设备拆图仅在测量证明有收益时继续。 |

MPI／多机分布式和跨设备模型切分不列入本轮优先实验：当前验收围绕单机四套权重，尚无需要模型分片解决的容量或部署要求。若未来出现多用户吞吐、多机任务或模型容量需求，再单独评估；不以 RMVPE 参数量推断 UVR 的适用性。

### 窗口依赖与流水线边界

[VR 音频路径](../core/src/vr/audio.rs) 先分析整段频谱，再用整段幅度最大值归一化所有窗口。因此不能在尚未确定全局最大值时直接启动等价的网络推理；提前流式推理需另行设计并验证两遍扫描等方案。全局前处理完成后，可按原索引分派独立窗口并写回各自有效 ROI，保留上下文、补零和参考的额外 ROI 规则。DeEcho 每窗仍须独立重置 LSTM 状态。

[RoFormer 音频路径](../core/src/roformer/audio.rs) 的窗口推理可作为独立任务，但输出存在重叠。每窗保留独立结果，按既定窗口索引执行 Hamming 加权累加和权重归一化，不能用并发浮点加法任意改变累加顺序。保持 8 秒窗口、重叠数 4、末窗对齐和裁剪规则，并沿用 float64 正向 STFT 约定；覆盖乱序完成、短输入、尾窗只执行一次以及接缝回归。RoFormer 的 Burn／Rayon 算子内部已经并行，窗口并发会形成嵌套线程池；在没有端到端稳定收益的证据前，默认 `UVR_ROFORMER_WINDOW_PARALLELISM=1`，该变量仅作为显式实验开关，不把 VR 的窗口并发收益推广到 1296。

流水线主要改善稳态吞吐，单窗延迟仍包含阶段耗时和排队；只有阶段可重叠且资源足够时，稳态间隔才可能接近最慢阶段耗时。若前处理与网络竞争同一 CPU、缓存或内存带宽，拆成多个线程可能更慢。先比较串行与一个明确重叠边界，再增加阶段，不预设“一阶段一线程”最佳。窗口准备／归并不等于当前整段 STFT／重建已能流式执行。

队列和乱序结果缓冲都须有容量限制，明确所有权以及消费完成或设备同步后才能复用 buffer 的时机。检查满队列、慢窗口、取消和错误传播，停止派发并回收任务，不能丢窗、重复处理或永久等待；阻塞 I/O 或相互等待的队列不要直接塞入同一 Rayon 计算池。当前 [文件任务](../core/src/file_task.rs) 在完整分离后准备两轨编码再发布，流水线仍须防止取消或失败时发布未完成音频。GUI 已使用后台任务，移出 UI 线程本身不作为推理加速证据。

### 线程预算、缓存一致性与扩展性

Rayon 在同一池中的嵌套 `join`／并行迭代复用固定工作线程，不会因为两层任务就自动产生“外层线程数 × 内层线程数”的 OS 线程。超额订阅应核查独立 Rayon 池、BLAS／OpenMP／后端池及同时运行的任务；即使没有超额线程，任务过碎、嵌套调度和负载不均也可能拖慢。记录每个池的配置、实际活跃线程、并发窗口数、核心集合与 SMT／混合核心拓扑，不只记录一个 `num_threads`。

如果单窗算子并行在少量核心上已停止扩展，而仍有独立窗口与可用资源，优先比较外层任务并行。例如在 16 个计算线程预算下，对照一个窗口使用 16 线程、两个窗口各使用 8 线程、四个窗口各使用 4 线程；这是实验分配示例，须确认后端实际执行预算，不能从嵌套 Rayon 的调用层数推断。分别测多个 batch=1 调用和真正的张量 batch，窗口不足时只报告该输入可提供的并行度。保留相同工作量、重叠／上下文和输出顺序，记录共享权重及私有激活／scratch 的内存，遵守 [窗口依赖](#窗口依赖与流水线边界)。不同文件也可另测批处理吞吐，但不能以多文件聚合倍速冒充单首歌加速；两轨 stem 可能共用一次掩码预测，不能默认每个 stem 都是一份独立网络任务。

False sharing 是多个核心访问同一缓存行中的不同数据，且至少一方写入，引发本可避免的缓存一致性开销；候选位置包括邻接的进度计数、输出分区边界和每 worker 的统计量。先用连续 tile 分区、私有 scratch 和局部归约减少共享写，再对热点测试对齐／padding，计入额外内存。只读共享权重不是 false sharing；平面步长导致的缓存组冲突是另一类问题。缓存行大小按实际硬件记录，不全局盲加 64 字节 padding；有条件时用缓存行争用采样交叉验证。

并行实验按以下顺序留存证据：

1. 固定同一模型、输入、窗口集合、精度、算法和 batch，测单线程 `T1` 与 `p` 个计算线程的 `Tp`，记录强扩展加速比 `S(p)=T1/Tp`、效率 `E(p)=S(p)/p` 和全部时间样本。线程数量不等于同等物理核心算力，混合核心／SMT 的结果需注明；对产品仍另报相对固定 2 线程基线的收益。
2. 在相同总计算线程预算下，分别比较算子内并行、窗口并行和独立分支并行；随后才组合并调整 batch。对每种调度固定工作量，不能用更多输入或减少重叠伪造扩展收益。
3. 同时观察墙钟与 user／sys 时间、IPC、缓存／带宽、核心迁移、上下文切换、任务／队列等待和峰值 RSS。扩展停滞可能来自串行比例、任务粒度、同步或带宽；不能单凭利用率或 cache-misses 定性。若估算算术强度，注明运算数与字节数口径，并与本机可持续带宽和相同精度的计算能力比较。
4. 将调度后的完整掩码与两轨音频纳入原质量门限，重复运行检查归并顺序和状态隔离，覆盖首尾／接缝、尾批、取消与失败。吞吐、首个进度、每窗／取消延迟及内存均需报告；Amdahl 上限、单核内核加速和流水线理想间隔均不能替代实测整文件收益。

## 编译器优化实验

分别验证两个层次：Rust／LLVM 优化已生成的循环、调用和机器码；保留张量图与 shape 信息的推理后端／图编译器负责跨算子的融合、布局传播、计划选择及内存复用。两者配合，但不能期待 `rustc` 从任意库调用和低层循环自动恢复整张神经网络图。下列均为候选实验，不直接修改发布配置。

### Rust／LLVM 构建矩阵

仓库根 workspace 尚无 release profile 覆盖。Cargo 在当前 Linux 基线下的默认 release 已包含 `opt-level=3`、`codegen-units=16`、`panic="unwind"`；`lto=false` 仍可能执行同一 crate 内 codegen unit 之间的 Thin Local LTO，不能标成“完全无 LTO”。执行时用 `cargo build -vv` 留存实际 rustc 参数，同时记录 Cargo 配置和环境覆盖、`rustc -vV` 中的 LLVM 版本、target triple、链接器及二进制摘要。

| 组别 | 配置 | 主要比较对象 |
| --- | --- | --- |
| A | 现有默认 release，通用目标 CPU | 性能、数值和可分发性的基线 |
| B | A ＋ `-C target-cpu=native` | 对 A 测本机指令选择与自动向量化收益 |
| C | B ＋ `lto="thin"` | 对 B 测跨 crate ThinLTO |
| D | B ＋ `lto="fat"`，codegen-units 保持默认 | 对 B／C 测 LTO 策略，避免同时改变多个因素 |
| E | D ＋ `codegen-units=1` | 对 D 单独测 codegen unit 数量；有必要时在 B／C 下交叉验证 |
| F | 已验证的 B～E 最佳配置 ＋ PGO | 对同一配置的非 PGO 构建测 profile 的增量收益 |

每组使用独立 `CARGO_TARGET_DIR`，输出放本地实验目录；同一二进制目标、feature、锁文件、线程／核心绑定、batch 和 shape 保持一致。通过 `RUSTFLAGS`、`CARGO_PROFILE_RELEASE_LTO`、`CARGO_PROFILE_RELEASE_CODEGEN_UNITS` 或独立实验 profile 设置候选参数，并记录完整值。主 workspace 与 `benchmarks/backend-probe` 是独立 workspace，构建设置与锁文件需要各自核对；探针获益后仍须验证实际 CLI／GUI。

各组报告完整窗口／文件耗时、RTF、峰值 RSS、每窗延迟，以及编译／链接时间、构建峰值内存和二进制大小。用 `perf stat` 比较 cycles、instructions、IPC、cache-misses、branch-misses 等可用计数器；计数器不支持或混合核心 PMU 口径不同须注明。采样与正式计时分开，尾延迟按本协议的样本数量要求报告。Fat LTO、单 codegen unit 和 `native` 均可能无收益或退化，不能因选项更激进就采用；可分发构建还须在通用 target 下重测选中的 LTO／PGO 配置。

`panic="abort"` 不纳入上述默认矩阵：GUI 的 [分离任务](../gui/src-tauri/src/tasks.rs) 和 [模型下载](../gui/src-tauri/src/models.rs) 用 `catch_unwind` 将 panic 转成任务错误。abort 会绕过此恢复路径并终止整个进程，也不执行栈展开析构。若另行研究，必须作为改变错误恢复语义的独立实验，验证实际 release 二进制中的故障处理和临时文件清理；普通 `cargo test` 的 unwind 测试不能证明 abort 行为正确。

### 自动向量化、reduction 与 FMA

LLVM 的 Loop／SLP 向量化由目标成本模型决定，release 或 `native` 不保证每个热点都被向量化。现有 GEMM 已采样到 AVX2/FMA 内核，应重点检查 Winograd 变换、重排、插值、逐元素运算和归一化等剩余热点；通过 `-C remark=all` 等与当前工具链匹配的诊断、优化后的 IR／汇编和运行采样交叉确认，避免仅凭源码形态判断。

先对连续切片、固定 stride、可证明的边界和数据依赖做局部对照，让编译器有机会消除冗余检查并生成向量代码。使用安全 Rust 的切片／迭代器表达约束；手写 SIMD 只有在诊断证明自动向量化不足且维护成本可接受时才进入后续实验。

浮点 reduction 的重关联以及 FMA 收缩会影响舍入，`target-cpu=native` 本身不等于允许这些语义变化。把 `a * b + c` 改为 `a.mul_add(b, c)`、拆成多个累加器或改变归约顺序，应各自作为数值算法实验；FMA 的一次舍入也不保证最终掩码更接近参考。先检查敏感中间张量，再走完整音频门限，尤其保留 1296 的 float64 STFT 与低能量频带回归。不通过门限的改动不与构建参数实验合并，也不全局放开 fast-math 来绕过 NaN／Inf 检查和精度约束。

### PGO 的采集与评估

1. 从已验证的配置创建独立插桩构建，使用 `-C profile-generate=<本轮绝对目录>`。每轮用新的实验目录或 `mktemp -d`，保留旧 profile；固定 `--target`，避免把目标端 PGO 参数施加给宿主构建脚本。记录源码、工具链、feature、目标 CPU、LTO 和 codegen-units。
2. 运行有代表性的 UVR 工作负载，包含实际音乐、默认 512 帧 VR 窗口、1296 完整 8 秒及短窗、尾块、单／双声道和重采样。保留各模型、文件格式和冷热任务的采集比例，静音跳过网络的路径不能代表主要推理工作量。只采集一种模型或 CLI 时明确覆盖范围，不能宣称对其他模型或 GUI 同样有效。
3. 用当前 Rust 工具链配套的 `llvm-tools-preview` 中的 `llvm-profdata merge` 合并 `.profraw`，保留原始文件及 `.profdata` 摘要。工具不自动加入 PATH，记录实际可执行路径与版本；不要混合旧版本或不同构建配置的数据。
4. 将 generate 替换为 `-C profile-use=<绝对路径.profdata>` 重建，其余影响代码生成的配置与采集构建一致。可加 `-C llvm-args=-pgo-warn-missing-function` 检查缺失 profile；记录缺失／不匹配诊断，确认优化确实消费了本轮数据。
5. 在独立于采集集的真实音频及边界样本上比较 F 与对应非 PGO 构建，先验证输出，再测热运行和尾延迟。插桩构建仅用于采集，其耗时不能计作优化结果。单列采集／二次编译成本，保留无 PGO 的回退产物。

PGO 可作用于本次插桩和编译覆盖的 Rust 依赖代码；预编译原生库、运行时 JIT 和手写汇编不会自动获得同样的变换。应按采样中的覆盖比例解释整网收益，而不是套用其他项目的 PGO 加速数字。

### 模型图编译与执行计划

这些实验延伸前述后端、融合和布局方向，优先利用成熟后端保留的模型图。MLIR／Linalg 是表达与实现相关变换的基础设施，不是可直接替换当前 UVR 后端的成品；引入时还需证明导入、算子语义、执行计划及 Rust 调用／分发路径可行。

| 编译方向 | UVR 试验对象 | 需要记录和验证的结果 |
| --- | --- | --- |
| Shape specialization | 按模型、VR 合法窗口及 batch 分别准备计划；1296 完整窗和短输入单独处理 | 计划创建／命中开销、生成代码大小、固定 shape 的收益；未覆盖尺寸的明确回退与尾窗长度正确性，不能只验证一种长窗 |
| 图融合与常量／权重折叠 | Conv–BN–激活、线性层 bias／激活及相邻逐元素节点；加载时处理常量权重 | 优化前后 IR／执行节点、kernel 数、中间写入和重排次数；确认融合实际发生，检查 BN epsilon、激活定义和严格权重身份 |
| 布局传播与多级 blocking | 卷积／线性层链、U-Net skip／concat 周围的布局，缓存和寄存器 tile | 后端选择的 block／layout、跨层保留范围、显式与隐式 reorder 字节数；收益必须包含最终转回输出格式的成本 |
| 内核选择与 autotuning | 按真实 shape、dtype、ISA 比较直接卷积、im2col、Winograd 和已有优化内核 | 所选算法／tile／线程、搜索成本、计划缓存命中及版本失效；先验证候选数值再调优，调优耗时与稳定推理分开报告 |
| 量化图编译 | 检查 Q／DQ、scale 的传播与融合，确认实际 INT8／浮点执行路径 | 转换节点数、回退和跨精度搬运、端到端收益；沿用独立校准／验证集和既定音频质量门限，不能只统计权重压缩比 |
| 静态内存规划 | 分析激活生命周期，复用 arena／workspace，保留 U-Net 长生命周期 skip | 实际分配次数和峰值内存；验证分支扇出、张量别名、任务取消、并发隔离及异步设备完成前的生命周期，零分配目标以测量为准 |

每个图级候选先在同一 Rust 编译配置下对照，再叠加选中的 LTO／PGO 构建；保存所用图、计划／内核选择和编译器版本。算法、图重写与机器码优化的组合需要重新验证，不能将各自加速比相乘作为实测结论。

## 实验顺序与推理结果可用性

1. 保存现有构建、输入、参考输出和采样记录；在固定 2 线程、FP32、batch=1 下获得基线。320 帧掩码可用于定位，产品评估仍须包含默认 512 帧窗口、完整音频和处理链。
2. 每个候选先验证真实算子／中间张量，再验证完整掩码和两轨音频。共享 VR 算子变更覆盖 5-HP、6-HP、DeEcho；只修改某一模型时明确验证范围。失败样本和未通过的候选保留记录。
3. 通过数值检查后执行一次额外预热和至少 5 次热测量；分开报告首次执行、模型准备和常驻内存。A→B→A 复测可检查热降频、系统争用和环境漂移；采样、参考生成、构建与正式计时顺序执行。
4. 先测单因素，再验证有收益的组合。算法／布局变更后重新测线程与 batch，避免组合调参掩盖收益来源。尾延迟保留全部每窗样本，样本不足时报告范围和最大值，不用 5 个样本宣称 p99 稳定性。
5. 采用现有 [工程基线的数值与质量门限](baseline.md#数值与质量验收)：完整音频每样本误差 `≤ 2e-4 + 2e-3 × abs(reference)`，误差 RMS `≤ 1e-3 × max(参考 RMS, 1e-4)`；声道、采样数、时间对齐和增益正确，静音严格为零，全轨有限。保留原权重和预设作为回归对照，不以独立归一化、平移或放宽门限掩盖退化。
6. 保存真实素材的两轨 WAV、残差及首尾／接缝片段供 A/B 试听，覆盖弱人声、和声、强混响和明显 echo；记录听评是否完成。数值通过只能证明与参考接近，不能替代输出语义和实际听感验收。检查取消后无部分正式输出、失败重试及 GUI 响应。
7. 只有同时改善目标耗时、满足质量门限及内存／交互预算，才更新默认配置；只在特定硬件或 batch 下获益的方案注明适用范围。不同精度、结构或音质预设另列实验，不能并入原预设的加速比。

## 外部方向的参考来源

以下资料用于确定试验方法，不作为 UVR 已获得相同收益的证据；查阅日期为 2026-09-11。实验报告另固定实际使用的库、执行提供程序和版本。

- [oneDNN 推理实践](https://uxlfoundation.github.io/oneDNN/dev_guide_inference.html)：布局传播、权重缓存、primitive 复用及融合 post-op。
- [ONNX Runtime 图优化](https://onnxruntime.ai/docs/performance/model-optimizations/graph-optimizations.html)：常量折叠、算子融合、布局优化及离线优化图；验证实际后端是否应用了相应优化。
- [OpenVINO CPU 设备](https://docs.openvino.ai/2026/openvino-workflow/running-inference/inference-devices-and-modes/cpu-device.html)：硬件／精度能力和实际执行精度；低精度支持与性能应按设备核实。
- [Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html) 与 [rustc codegen options](https://doc.rust-lang.org/rustc/codegen-options/)：release 默认值、LTO、codegen-units、panic、目标 CPU 和优化诊断。
- [Rust PGO](https://doc.rust-lang.org/rustc/profile-guided-optimization.html)：采集、合并、使用 profile 的配置一致性及缺失数据诊断。
- [LLVM 向量化](https://llvm.org/docs/Vectorizers.html)：Loop／SLP 成本模型、向量化诊断及浮点 reduction 的语义限制。
- [MLIR Linalg](https://mlir.llvm.org/docs/Dialects/Linalg/)：保留高层算子信息以进行 tiling、fusion、向量化及向库调用／目标指令的 lowering。
- [Rayon join](https://docs.rs/rayon/latest/rayon/fn.join.html) 与 [ThreadPool](https://docs.rs/rayon/latest/rayon/struct.ThreadPool.html)：固定池、work stealing 与嵌套任务复用，以及阻塞 I/O／相互等待的限制；实际实验固定锁文件中的 Rayon 版本。
